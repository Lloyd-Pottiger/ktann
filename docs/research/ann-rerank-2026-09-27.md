# Cohere1M rerank 150 / 125 / 100 对照

日期：2026-09-27。延续 [固定索引基线与缓存实验](ann-baseline-2026-09-26.md)。源码基线 `3a62957c458a87b5b708af58ea1975c679e54ac2`。

## 结论

- **1.25k 在本次查询集上足够。** 125与150逐查询recall完全相同。逻辑读取量减少16.0%，两次CPU/query均低于两次150对照，平均减少1.8%。减少读取和精排工作的机制已验证。
- **整体提速幅度小，证据为方向性支持。** 125的平均运行级QPS提高2.5%，p95降低2.9%，但QPS范围与150重叠，只有两次重复，不能声称稳定的2.5%端到端提升。
- **不采用100作为本场景的优化结论。** recall从0.92889降到0.92277（下降0.612个百分点），394/1000个查询退化，最差额外丢失4个真邻居；平均QPS仅提高1.0%，平均运行级p99反而增加5.9%。它仍满足recall>0.9，但未证明同等recall下的收益。

保留125作为这个固定工作负载的候选配置和实验记录；生产默认保持现有k派生规则（k=100时为150）。本轮未引入生产性能实现，未修改建树与import。

## 条件

Cohere1M，cosine，k=100，beam=384，RocksDB，partition cache 上限1 GiB，8个执行器 worker，4个并发搜索。全部复用同一份索引；唯一配置变量是现有公开 API 的 Runtime exact rerank budget。该预算也限制局部/全局候选集合，不能将所有变化都归为最后一步精排。

三个诊断组各执行1,000个不同查询；每个查询先执行不收集归因的对照，再执行归因版本，验证输出ID、距离位模式、usage、exhaustion和overlap标志一致。按相同确定顺序逐查询比较recall。诊断不用于性能结论。

正式计时使用编译时移除诊断hooks的同一个可执行文件，按150→125→100→100→125→150顺序，每组预热1,000次，测量2,000次；测量是同一批1,000个查询重复两遍。下表均值为两次运行级指标的算术平均，不是合并分位数。

预算同时作用于局部候选截断：150/125/100平均每查询在局部cap删除0/25.155/1884.232个候选，本批查询的真邻居均未在此丢失。100的近似筛选平均耗时约45.66ms，比150的43.67ms更高，抵消部分精排节省；局部截断工作增加是可观察的解释线索，尚未做更细粒度CPU profile来独立证明它贡献了全部耗时差异。

## 证据边界与复现

38项benchmark单元测试通过；相关Clippy（包含quality-diagnostics）和格式检查通过。9次有效完整数据集运行全部成功，报告、日志、可执行文件hash已校验。每次运行前后完整逻辑索引hash均为 `2faed35a66813167e55d0761152a619afa7250a3f1a17d4c2eb6ff04f3e32655`，最终索引完整性验证通过。

首次150诊断在查询与完整性检查后，被原多beam frontier校验拒绝；修复harness对单beam的支持后重新执行全部对照，失败产物保留，未纳入结果。每组查询数量及预算样本数检查继续生效。

实验材料位于 `.benchmark-data/results/ann-baseline-2026-09-26/`：`RERANK-PROTOCOL.md`、`prepare_rerank.py`、`prepare_rerank_single.py`、`run_rerank.py`、`rerank_sweep.py`、`analyze_rerank.py`、`rerank-summary.json`、`rerank-comparison.json`、`rerank.patch`、两个冻结可执行文件及各运行的report/log/provenance。实验代码位于已有独立worktree；生产默认未修改。

本轮只验证固定树、固定beam、k=100、无过滤器、warm-cache RocksDB场景。没有验证其他数据集、k、过滤器或FoundationDB，不能据此统一降低全局默认倍率。
