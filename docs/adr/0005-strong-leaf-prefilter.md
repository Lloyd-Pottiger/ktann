# Keep exact filter projections and strong leaf synopses

Each Leaf Entry duplicates the record's exact typed filter fields, while each leaf stores a strong conservative synopsis using NULL flags, per-field persisted min-max configuration, and at most four explicitly configured Bloom filters. Values have one explicit NULL representation; strings compare by raw UTF-8 bytes without collation or normalization, and finite f64 values canonicalize negative zero so comparison, Tree Key encoding, and Bloom hashing agree within an index. One schema-ordered, independently versioned binary codec stores each field's synopsis kind, NULL flags, canonical typed extrema, and optional Bloom parameters and bits. Predicate evaluation and synopsis extrema share the same typed comparator: `false < true`, numeric order for i64 and finite f64, raw UTF-8 byte order for strings, and no min/max value for NULL.

Synopsis evaluation internally returns a bit mask of SQL truth values that may occur among the leaf's entries: TRUE, FALSE, and UNKNOWN. The mask ranges over the monotonic historical Synopsis, which is a superset of current entries. Atomic comparisons derive a conservative mask from NULL flags and min-max; Bloom evidence may exclude a value and help prove NoMatch but a hit never proves presence or TRUE. AND, OR, and NOT combine masks with the SQL three-valued truth tables, so NOT swaps TRUE and FALSE possibilities but preserves UNKNOWN. The public pruning result is `NoMatch` if TRUE is impossible, `AllMatch` if TRUE is the only possibility, and `MayMatch` otherwise. Stale extrema/NULL history can weaken AllMatch but cannot make it unsound. Search may omit per-entry predicate evaluation for `AllMatch`; all other visited entries still use their exact Leaf Entry fields. This retains correct arbitrary-NOT behavior that a direct three-state negation cannot provide when NULL is present.

Bloom configuration exposes expected distinct values and target false-positive rate, deterministically persists derived bit/hash counts, and never makes capacity or saturation a correctness or split condition. Creation rejects a configuration whose complete encoded synopsis would exceed 64 KiB rather than silently weakening the requested false-positive rate. Canonical typed values are hashed with a codec-versioned, domain-separated XXH3-128 seed; its two halves drive double hashing `h1 + i*h2`. Saturation only reduces pruning until entries move into newly empty split partitions. Foreground writes serialize synopsis expansion with entry changes, and delete/update never shrink a source synopsis. A new split target starts from the canonical empty synopsis; every actual Leaf Entry move atomically expands only its actual target, and merge uses the same rule. No completion-time rescan or whole-source union occurs, so unrelated source values do not contaminate several targets. An empty leaf has an empty possible-truth mask and therefore yields NoMatch. The added write contention and storage make pre-filter pruning safe without reading source records, while exact Leaf Entry evaluation guarantees the returned filter contract. Tree Key fields need no synopsis because tree routing already constrains them, but may opt in like other fields.
