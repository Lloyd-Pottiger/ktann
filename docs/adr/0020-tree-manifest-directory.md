# Use Tree Manifests as the forest directory

Each lazily created Tree Key has one Tree Manifest that is atomically installed with its root, serves as the key-only directory entry for broad-query enumeration, and stores the per-tree Partition Key allocator high-water mark. KTANN deliberately introduces no separate Tree ID: the canonical Tree Key is embedded directly in every tree, partition, and entry logical key, and Record Location stores that Tree Key alongside its leaf Partition Key. This keeps one tree identity and removes an allocator and directory lookup from point routing, at the accepted cost of repeated key bytes, comparison work, and transaction-size amplification.

The Tree Key uses an independently versioned memcomparable tuple codec whose byte order matches the typed predicate comparator and supports field-prefix half-open scan ranges; it does not reuse the value codec. Its fully encoded form is limited to 8 KiB. Create computes the maximum possible encoded Tree Key from the selected field schema and rejects a configuration that could exceed it, so every schema-valid record respects the limit; mutation still performs the exact defensive length check. Physical backend encoding must append the already-canonical bytes without an unbounded second escaping pass.

Processes update-protect the Tree Manifest only when reserving a default 1,024 Partition Key range, not for every partition; empty trees and their manifests remain until index drop. Ordered directory scans are forward-paged within remaining key and backend byte limits so a broad query neither touches partition data nor performs budget-external read-ahead.
