# Store partition authority and entries as independent KV values

A partition stores authority State, immutable Centroid, exact-count/cache-epoch Header, strong Synopsis, and each Child or Leaf Entry as independently addressable KV values. Compared with rewriting one monolithic partition value, this layout reduces write amplification and enables bounded structural moves, but same-leaf foreground mutations still serialize through the Header and Synopsis keys to preserve exact counts and strong pruning summaries.

Vector Record, Record Location, and optional Opaque Payload are also separate values. Location contains the canonical Tree Key and leaf Partition Key, allowing structural moves to update only the small authority mapping rather than rewrite the original vector, fields, or payload; point reads recover all requested pieces with one batch-get. All data owned by one Logical Index ID occupies one continuous physical range, while its name Manifest and the namespace-level ID allocator remain outside that range, so drop can clear exactly one range before deleting the Manifest.

Within that range, physical locality follows access ownership rather than value type. Record, Location, and Payload keys are adjacent under each Record ID. The Tree Directory is a separate Tree-Key-ordered range so broad enumeration reads exactly one item per tree. All other tree data is grouped first by canonical Tree Key and then Partition Key; State, Centroid, Header, Synopsis, and every Child or Leaf Entry share that partition prefix. This makes one partition a contiguous clearable range and keeps tree-local traversal and maintenance adjacent, at the cost of repeating the Tree Key already accepted by the no-Tree-ID design. Logical Index ID and Partition Key are nonzero fixed-width big-endian u64 values; zero is invalid. Tree Key and Record ID components use one self-terminating memcomparable encoding pass.

Persistent values use their type tag, codec version, lengths, and structural validation but no application CRC; backend storage checksums own physical corruption detection. Removing a partition point-deletes its fixed metadata and clears its entry prefix when the backend supports transactional range clear. Otherwise it performs bounded paged entry deletion while retaining the partition's structural intermediate state until the range is empty.

Fallback partition deletion scans and point-deletes one bounded page inside a write transaction that update-protects and revalidates the source's terminal maintenance state. Only an empty page permits the same protocol to perform its final parent/topology switch and metadata deletion, so a stale worker cannot delete a live partition. Drop applies the analogous loop to the whole data prefix: every chunk update-protects the same name Manifest in Dropping with the same Logical Index ID, and an empty page permits Manifest deletion. Unknown commit outcome restarts at the prefix beginning; already-deleted leading keys make this naturally resume without a persistent delete cursor.
