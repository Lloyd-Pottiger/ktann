# Expose split targets before draining their source

A split first persists target identities, then uses a multi-transaction protocol that creates and exposes each target separately before marking the source Draining. This accepts durable partially published states so every transaction stays small and each step can be retried independently. While the source is Splitting, foreground writes may continue changing it. Leaf training therefore reads all source entries and their Vector Records through one consistent snapshot, closes that transaction, and runs K-means without holding KV locks; target centroids are a routing model learned from that snapshot, not an authoritative description of later membership. Publishing targets does not validate a whole-partition epoch or restart merely because concurrent writes changed the source. After the source becomes Draining, inserts are redirected and migration reloads authoritative current membership.

The root remains Partition Key 1 and is promoted only after its entries move. This protocol accepts that target centroids may lag concurrent changes, along with searchable partially published states and routing retries, to avoid long write transactions and split-versus-ingest conflicts; exact atomic movement rather than centroid freshness preserves membership correctness. Split training deliberately has no additional sampling, memory, or CPU bound: even an abnormally enlarged source trains from its complete snapshot, favoring centroid quality and one simple training rule at the cost of resource use proportional to source size.

Each new target is `ReceivingSplit { source }`: it is searchable, accepts redirected and migrated entries, and supports exact delete, but cannot itself split or merge. The first successful unique creation fixes the left target centroid. A competing or recovering worker that observes that target pins its persisted centroid when recomputing the right centroid; an already-created right target likewise keeps its persisted centroid. For a non-root source, each target's unique creation and parent Child Entry insertion are one transaction; left and right targets are still installed in separate transactions. That transaction update-protects the traversed parent and verifies that it still contains the source Child Entry and accepts a new child; failure abandons the step so a later traversal can rediscover the source's current parent. A root target instead occupies an exclusive target slot persisted in Partition Key 1 until the root exposes it. Each installation also update-protects the source State and verifies that it is still Splitting and names that target, preventing orphans and preventing a stale worker from recreating or relinking a target after the source advances without retaining permanent partition tombstones.

The transition to Draining update-protects the source and verifies that both targets identify it as their source. It does not rediscover or revalidate their current parent references: target installation established one exact incoming Child Entry, and adjacent-level maintenance may subsequently move each entry, even to different parents, without reading target state. The root has no parent and exposes its targets through its Draining state. This transition deliberately ignores source entries, count, and cache epoch so concurrent foreground writes during training and publication do not abort the structural operation. A target becomes Ready only after its source has been fully drained.

Draining does not block foreground data changes. A new insert routes directly to the nearer target; an upsert whose Record Location still names the source atomically removes its source entry and inserts into the nearer target; and exact delete follows the current Record Location whether it names source or target. These mutations update-protect the relevant topology states and replay as a whole if those states change.

A leaf drain first obtains a bounded batch of Record IDs from a short read snapshot, then opens a write transaction and re-reads each source entry, Record Location, and Vector Record. An entry removed by a concurrent completed mutation is skipped; a remaining entry inconsistent with its record or location is corruption. The current Vector Record is normalized and rotated, then routed against the two persisted target centroids with a Partition Key tie-break; its unchanged absolute RaBitQ7 payload is copied rather than re-encoded. No durable cursor is stored: each batch starts at the source's current smallest entry because successful moves delete that prefix. Internal drains apply the same exact source-delete/target-insert rule to Child Entries but need neither Record Location nor Vector Record reads.

An internal split trains outside its read transaction from the complete consistent-snapshot set of full-f32 Child Entry centroids. During draining, it reloads each current Child Entry and routes that centroid against the two persisted target centroids, atomically moving the entry and both exact Header counts. It does not read the referenced child partition's state: child and parent maintenance are independent, and exact Child Entry ownership is the coordination point. Internal and leaf splits use the same state protocol and zero-count completion; internal partitions simply omit Record Location, Vector Record, and Synopsis work.

A non-root Draining split also performs bounded same-level correction for both partition kinds. The routing vector is the current Vector Record at level 1 and the immutable Child Entry centroid above level 1. Source entries may move to a Ready sibling only when it is strictly closer than both ReceivingSplit targets and both target minima remain attainable; entries from a Ready sibling or cousin may move into a ReceivingSplit target only when the target is strictly closer than their current owner's centroid. Partition Key resolves equal distances, so equality never causes movement. One typed topology operation owns the legal state matrix and atomic bookkeeping: `DrainingSplit` may target its own `ReceivingSplit` family or a same-level `Ready` partition, while a `Ready` source may target only the named `ReceivingSplit` family. It update-protects all participating authority, validates levels and family identity, uniquely inserts before deleting the old membership in the same transaction, and rechecks corrective capacity. Leaf moves also update Record Location and target Synopsis; Child Entry moves preserve exactly one incoming parent edge. A competing split or merge state change therefore conflicts and is replanned rather than repaired after commit.

Corrective discovery is approximate but explicitly bounded. It traverses from the root with a maintenance-only beam of 16, expands at most 16 partition bodies per level, reads at most one 128-entry/1-MiB Child Entry page per body, and retains at most 16 same-level Ready candidates. Each pull pass rotates through at most four retained candidates and reads at most one 128-entry/1-MiB entry page from each: at most 512 entry envelopes are scanned, while a rotating deterministic aggregate sample screens at most eight routing vectors so fixed candidates and low-ID prefixes do not monopolize repeated rounds. Encoded Backend mutation budgets separately cap the entries selected from a page. Fully exposed transitional split families contribute their validated source and target bodies, while a partially exposed ReceivingSplit target redirects to its still-complete Splitting source body. The split source and targets are excluded at the candidate level, and a root split naturally skips correction. This adds bounded maintenance reads and distance work without changing foreground `write_beam_size` or refreshing existing Child Entry centroids. The internal 128-entry relocation limit is only a contention cap and may be reduced by the encoded mutation budget.

A corrective pull from a Ready internal partition retains at least one Child Entry. Planning excludes one-entry donors, the write attempt re-caps the batch against the update-protected source Header, and the topology boundary rejects a batch that would empty the source. This preserves a routable body behind every Ready partition's incoming Child Entry; ordinary split and merge sources may still drain to zero under their structural protocols.

The exact update-protected Header count is the sole authority for source emptiness; completion does not repeat an entry scan. One short final transaction verifies the corresponding Draining state and zero count, promotes both targets from ReceivingSplit to Ready, and switches the topology. For a non-root it removes the source Child Entry and deletes the source State, Header, Synopsis, and centroid metadata; for the root it converts Partition Key 1 in place into a Ready internal root containing the two target Child Entries. Atomic entry moves and Header updates are the invariant, so a redundant empty-range check would add I/O and implementation complexity without strengthening the contract.
